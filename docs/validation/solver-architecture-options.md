# Alternate-backend feasibility assessment — 2026-09-12

This is an API assessment and proposed experiment, not a replacement implementation or a claim that another engine passes. The accepted design explicitly selects Havok. Replacing it requires an architectural decision; no dependency, backend code, or production behavior changes here.

> **Superseded API detail:** The pinned 0.20.0 package now exposes a native motor cap, verified by independent rotor dynamics. See [the executable probe and current decision](solver-api-probe/README.md). The friction-equivalence blocker remains. The table below records the earlier documentation-only assessment.

## Rapier capability and gaps

| Requirement | Documented JavaScript capability | Implication |
|---|---|---|
| Fixed 120 Hz, controlled solver accuracy | `IntegrationParameters.dt`, `numSolverIterations`, `numInternalPgsIterations`, `normalizedAllowedLinearError`, `normalizedPredictionDistance` | A bounded iteration-convergence experiment is possible without changing the external tick. The allowed-error parameter controls engine correction, not the independent 1 mm acceptance threshold. |
| Original solid dimensions | Cylinder, cuboid, convex-hull and rounded shapes; explicit mass/COM/principal inertia | Preserve the actual two circular rods and two rounded rectangular rods, rather than replacing all four with cylinders. Reuse the prize's bevel vertices and physical mass tensor; do not copy Havok's mass-normalized inertia directly. |
| Distinct static/dynamic friction | The official guide states that Rapier does not distinguish these coefficients | The current 0.34/0.26 material model has no direct equivalent. A kinetic-only 0.26 probe is useful, but cannot certify full profile equivalence. |
| Finite native hinge-motor torque | Public `RevoluteImpulseJoint` API lists motor model/velocity/position configuration, but no maximum-force/torque setter | The guide mentions maximum motor impulse generally, but an applicable shipped JS setter has not been established. Do not equate `configureMotorVelocity`'s factor with a torque cap. |
| Explicit capped actuator alternative | Rigid-body torque and torque-impulse application | Equal-and-opposite clamped actuator torques can represent a finite physical actuator. This changes implementation from Havok's native implicit velocity motor and requires separate calibration; it is not a verified drop-in replacement. |

Solver controls are documented in [IntegrationParameters](https://rapier.rs/javascript3d/classes/IntegrationParameters.html). Geometry, explicit mass properties and the friction limitation are documented in the [JavaScript collider guide](https://rapier.rs/docs/user_guides/javascript/colliders/). Motor methods are listed in the [RevoluteImpulseJoint API](https://rapier.rs/javascript3d/classes/RevoluteImpulseJoint.html); broader motor prose in the [joint guide](https://rapier.rs/docs/user_guides/javascript/joints/) does not establish a missing JS cap setter. Explicit torque application is described in the [forces and impulses guide](https://rapier.rs/docs/user_guides/javascript/rigid_body_forces_and_impulses/).

## Proposed bounded proof before any app migration

1. **Pin and inspect an exact published package.** Verify compiled JS/WASM motor-cap and contact-modification APIs. If there is no exposed cap, stop the native-motor path. If distinct static/dynamic friction cannot be represented through documented APIs, label full material equivalence blocked; do not silently collapse the coefficients.
2. **Port only headless geometry/mass fixtures.** Use the existing four rod profiles, original prize size, initial position, mass blocks, COM and physical inertia. Independently check mass and angular response with a known impulse. Hold gravity at 9.80665 m/s² and actual step at 1/120 s. No scene UI or sequence rewrite.
3. **Predeclare a numerical comparison.** Compare 4, 8 and 16 solver iterations with one declared small correction allowance (e.g. 0.1 mm, one tenth of the unchanged 1 mm gate) and fixed prediction/skin settings. Report every configuration, timing cost and any nonconvergence. Do not select isolated favorable trajectories.
4. **Measure contacts and kinetic sliding.** Sample all contacts from initial settling onward. Cross-check signed contact depth with a separate geometric shape-distance calculation at post-step poses. Repeat the exact original sliding apparatus, initial speed and endpoint interval; retain the independently derived vertical-momentum target and normal/damping/slip guards. Use 0.26 only for this explicitly kinetic-only diagnostic; it is not a passed static-friction model.
5. **Prove a finite-torque obstructed hinge.** Use the original arm dimensions/inertia, real joint axis/limits, original 0.08/0.12/0.18 m load-cell openings and existing torque/force envelope. If native cap exists, measure angular impulse divided by actual dt. Otherwise, an explicitly clamped equal-and-opposite torque controller must have a documented law, verify angular momentum with a known torque impulse, saturate at the reduced limit, and pass load-cell force and locked-axis bounds. Never apply actuator forces directly to the prize.

Only success across geometry, contact, material compatibility and finite-actuator tests would justify proposing an app adapter. Full 20-cycle, reset/Continue identity, pause/axis locking, browser behavior and performance remain separate gates after integration. The present evidence establishes a Havok configuration limitation for this fixture, not global impossibility and not a guaranteed Rapier fix.
